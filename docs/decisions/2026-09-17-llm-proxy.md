# 決定：報價 LLM 第二層經 wa-inbox proxy — 「唔准入 prompt cache」界線拍板

**日期**：2026-09-17（cwi-final S2-9 spec ⑧）
**狀態**：已拍板
**範圍**：workforce `apps/web/src/lib/clinical/llm-client.ts`（S2-9b D-2，commit 見 git log）+ wa-inbox `/api/internal/llm-extract`

## 結論

接受 sglang KV cache（RadixAttention），**唔加** `--disable-radix-cache`。

## 界線分析

- **wa-inbox 應用層**：冇任何 cache（route 唔寫 Redis 除 nonce、唔寫 DB、唔寫檔）✅
- **sglang**：RadixAttention 係**成部 sglang server 共用一棵** prefix 樹（GPU 記憶體；LRU 淘汰；重啟即清；冇 API 讀得返）。**唔會令唔同病人混淆**，原因：
  1. model 冇狀態、冇「對話」概念 — wa-inbox 每次都由 DB 攞**該對話**嘅訊息重新砌 prompt（`ai.worker.ts:206-213` `where: { conversationId: conv.id }`）；proxy 每次請求只帶一份 note
  2. cache 只重用「逐 token 完全一樣」嘅開頭（實際上 = system prompt／字典）；病人內容每份唔同，一定重新計；重用結果同重新計數學上一樣
  3. 同一時間多個請求一齊跑（batching），attention 只睇自己請求嘅 token
- **唯一理論風險** = 計時側信道（可以直接打 sglang 嘅人，憑回應快慢估某段文字最近有冇出現過）→ 靠「sglang 只准內部連」防。

## GPU 機啟動參數人手檢查三項（結果記入本檔）

1. sglang port 只 bind 內網／經 SSH 隧道，公網打唔到
2. **冇** `--log-requests`（會 log 原文）：`ps aux | grep sglang | grep -c -- --log-requests` = 0
3. **冇** `--enable-hierarchical-cache`（HiCache 會將 KV 放落主機記憶體甚至外部儲存）：`ps aux | grep sglang | grep -c hierarchical` = 0

> 執行位置：GPU 機（server 側手動），唔喺任何 repo 可驗證範圍 — 每次 sglang 重啟後重做，結果回報入本檔。
